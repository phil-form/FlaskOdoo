# 04 — Migrations (Alembic / Flask-Migrate)

Fichiers: `migrations/`, `sqlAlchemy.sh`

## Pourquoi ne pas utiliser `db.create_all()`

`db.create_all()` crée les tables manquantes et s'arrête là: il ne sait pas
ajouter une colonne à une table existante, ni renommer, ni transformer des
données. Dès qu'une base contient des données qu'on ne veut pas perdre — donc
dès qu'on est en production, ou juste après le premier `/seed` — il faut des
migrations.

Une migration est un fichier Python versionné qui décrit **un pas** de
transformation du schéma, avec sa marche arrière:

```python
revision = '2b86203c0955'
down_revision = 'f4908d7d2d8d'   # la migration précédente: c'est le chaînage

def upgrade():   ...             # aller
def downgrade(): ...             # revenir
```

Alembic garde dans la base une table `alembic_version` contenant la révision
courante. Il en déduit les fichiers à appliquer.

## Le script sqlAlchemy.sh

```bash
./sqlAlchemy.sh -i                    # flask db init   (une seule fois par projet)
./sqlAlchemy.sh -m "nom_migration"    # flask db migrate -m "..."  (autogenerate)
./sqlAlchemy.sh -u                    # flask db upgrade
./sqlAlchemy.sh -e                    # flask db revision --autogenerate
```

Le script se contente d'exporter `FLASK_APP=app` et de lancer la bonne commande
`flask db`. Autres commandes utiles, à taper directement:

```bash
flask db current                       # où en est la base ?
flask db history                       # la liste des migrations
flask db downgrade <revision>          # revenir en arrière
flask db downgrade -1                  # reculer d'un pas
flask db stamp head                    # marquer la base à jour SANS rien exécuter
```

## Le cycle de travail

1. Modifier un modèle (`app/models/item.py`).
2. `./sqlAlchemy.sh -m "ajout couleur item"` — Alembic compare les modèles à la
   base et **écrit** le fichier de migration.
3. **Relire le fichier généré** — l'en-tête dit lui-même
   `# ### commands auto generated by Alembic - please adjust! ###`.
4. `./sqlAlchemy.sh -u` — appliquer.
5. Commiter le fichier de migration avec le changement de modèle. Une migration
   déjà appliquée ailleurs ne se modifie plus: on en crée une nouvelle.

Pour que l'autogenerate voie une table, son modèle doit être **importé**. C'est
le rôle de `from app.models import *` dans `app/__init__.py`: un modèle oublié
produit une migration vide (ou, pire, un `drop_table` si Alembic croit la table
en trop).

## Ce qu'Alembic ne devine pas

L'autogenerate compare deux schémas. Il ignore totalement le contenu des tables.
Cas rencontré dans ce projet — ajouter `email` NOT NULL et unique sur une table
`users` qui contient déjà des lignes. Alembic propose:

```python
batch_op.add_column(sa.Column('email', sa.String(120), nullable=False))
```

et PostgreSQL refuse: il faudrait mettre *quelque chose* dans la colonne pour
les lignes existantes. `server_default=''` ne sauve pas la situation puisque la
colonne est unique (deux chaînes vides = doublon).

La recette, en trois temps (voir
`migrations/versions/2b86203c0955_roles_items_baskets.py`):

```python
# 1. colonne facultative
op.add_column('users', sa.Column('email', sa.String(120), nullable=True))

# 2. remplir les lignes existantes — op.execute() envoie du SQL brut
op.execute("""
    UPDATE users
       SET email = username || '@example.local'
     WHERE email IS NULL
""")

# 3. rendre la colonne obligatoire
op.alter_column('users', 'email', nullable=False)
```

Même logique pour un renommage: `op.alter_column('users', 'mail',
new_column_name='email')` conserve les données, alors qu'un `drop_column` +
`add_column` les perd. L'autogenerate, lui, propose souvent la seconde version:
il ne peut pas savoir que les deux colonnes sont « la même ».

## batch_alter_table

```python
with op.batch_alter_table('users', schema=None) as batch_op:
    batch_op.add_column(...)
    batch_op.create_index(...)
```

SQLite ne sait presque rien modifier avec `ALTER TABLE`. Le mode *batch*
contourne cela en recréant la table puis en recopiant les données. Sur
PostgreSQL c'est inutile mais inoffensif — et ça garde la migration portable.

## Insérer des données dans une migration

C'est possible, avec `op.execute()` ou `op.bulk_insert()`, et c'est le bon
endroit pour des données **structurelles** dont le code a besoin pour
fonctionner (les rôles USER/ADMIN, par exemple).

Ce projet a fait un autre choix: les rôles sont créés par `RoleSeed`
(voir [12-seeding.md](12-seeding.md)), plus simple à relancer et à lire pour une
formation. Retenez la distinction:

| | migration | seed |
|---|---|---|
| contenu | données indispensables au fonctionnement | données de démo/test |
| exécution | une fois, dans l'ordre du chaînage | à la demande, idempotent |
| en production | oui | jamais |

## Dépanner

**« Target database is not up to date »** — la base n'est pas à la dernière
révision. `flask db upgrade` avant de créer une nouvelle migration.

**Autogenerate détecte des changements imaginaires à chaque fois** — souvent un
`server_default` écrit différemment dans le modèle et dans la base. Vérifiez que
la migration correspond bien au modèle: après un `upgrade`, un
`flask db migrate` doit annoncer `No changes in schema detected`. C'est le test
qui prouve que schéma et modèles sont alignés.

**La base est dans un état incohérent en développement** — la solution rapide,
et uniquement en développement:

```bash
docker compose down -v            # supprime le volume, donc la base
docker compose up -d db-example
./sqlAlchemy.sh -u                # rejoue toutes les migrations
# puis /seed
```
